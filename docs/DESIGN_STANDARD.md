> **Permanent rule of the road.** Part of the master system.
> Referenced in CLAUDE.md.

## RULE 0 — MODEL DECLARATION (DESIGN TASKS)

Every visible design task must begin with an explicit model declaration:

```
MODEL: <model name and version>
WHY: <one sentence — why this model is appropriate for this specific task>
```

**NGW model tiers:**

| Model | Role |
|-------|------|
| **Sonnet 4.5** | Default execution model — implementation, mechanical parity, visual verification, routine fixes |
| **Opus 4.1** | Escalation model — flagship direction, iconic visual language, creative direction, any task where weak taste or weak strategic judgment would create expensive downstream mediocrity |

Escalate to Opus 4.1 when: the task sets visual language, defines direction other work will follow, judges iconic potential, makes creative direction calls, or produces output that will be hard or costly to reverse if the taste call is wrong.

Stay on Sonnet 4.5 when: the task is mechanical execution of an already-locked direction, a spacing/copy fix, a parity check, or a validation pass with no open creative judgment calls.

This applies to: design critiques, Figma passes, social object design, export format work, creative direction, visual reviews, parity passes, and any task producing visible output judgment.

The model declaration is not boilerplate. It is a forcing function: if you cannot justify Sonnet for a direction task, use Opus.

## CORE POSITION

We are not trying to make the UI merely good.
We are trying to make it iconic, undeniable, memorable, and high-status.

Every visible UI/export/surface must survive ruthless design scrutiny before it deserves implementation.

- If it is technically correct but visually generic, it fails.
- If it is polished but forgettable, it fails.
- If it is tasteful but lacks force, it fails.
- If it feels like every other premium AI/productivity/creator SaaS, it fails.

---

## RULE 1 — FIGMA FIRST FOR VISIBLE DESIGN

Any significant visible design change must be proved in Figma before it is treated as resolved.

Applies to: screen redesigns, component redesigns, export formats, panel hierarchy, CTA hierarchy, empty states, visual language shifts, social surfaces, premium/art-direction passes, visual parity work that changes user-facing structure or tone.

**Exception — tiny fixes that skip Figma only if ALL of the following are true:**
- copy-only
- spacing-only
- obvious bug
- no hierarchy change
- no visual-language change
- no new interaction model

If any are false, Figma is required.

---

## RULE 2 — FIGMA IS A TEST LAB, NOT A DECORATION TOOL

Use Figma to test: hierarchy, force, distinctiveness, screenshot resilience, social magnetism, platform fit, thumbnail readability, multi-device behavior, premium feel, whether the design actually says something.

Do NOT use Figma to: make things neater, produce static documentation of mediocre ideas, or create five nearly identical safe options.

---

## RULE 3 — ICONIC OR FAIL

Every important visible surface must be judged against:

**Would a serious user remember this one week later?**

Also ask:
- Would someone screenshot this and repost it?
- Would another product be embarrassed to look this generic next to it?
- Does this feel unmistakably NGW before the logo appears?
- Does this create status for the user?
- Does this communicate force, taste, and point of view?

If the answer is no, the work is not done.

---

## RULE 4 — RUTHLESS CRITIQUE STANDARD

Critique must be brutally direct, specific, and unsentimental.

Do not praise work for being: clean, solid, polished, nice, good, production-ready — unless it is also distinct, forceful, and memorable.

Critique must identify:
- where it becomes generic
- where hierarchy weakens
- where the design loses nerve
- where it feels templated
- where it becomes decorative instead of powerful
- where it explains instead of compels
- where it looks like SaaS instead of NGW
- where it is merely premium-ish instead of iconic

Critique must push toward: stronger hierarchy, stronger point of view, more emotional precision, more authority, more social magnetism, clearer product identity, more inevitability, less filler.

---

## RULE 5 — WORLD-CLASS BAR

Judge all visible work against a world-class standard across:
- mobile phone
- tablet / iPad portrait
- tablet / iPad landscape
- laptop
- desktop
- large modern monitors used by visual professionals

Mobile-first remains the priority. But "looks good on mobile" is not enough if it falls apart on desktop or large monitors.

---

## RULE 6 — NO GENERIC PREMIUM BS

**Reject these fake-premium shortcuts:**
- over-glow
- obvious glassmorphism
- lazy black-on-black cards
- decorative gradients doing the work of hierarchy
- random gold for "luxury"
- generic fintech premium UI language
- generic AI app visual tropes
- crowded data density posing as seriousness
- overdesigned badges
- social-media-native fluff
- generic creator SaaS panel styling

**Premium must come from:**
- restraint
- hierarchy
- surface intelligence
- proportion
- typography
- spatial tension
- confidence
- clear point of view

---

## RULE 7 — STUDIO MATTE NON-NEGOTIABLE

All visible design work must preserve Studio Matte aesthetics unless code truth explicitly proves otherwise.

**Studio Matte means:**
- dark, cinematic, restrained foundation
- matte, not glossy
- subtle material depth
- quiet but deliberate accents
- controlled negative space
- serious instrument-like tone
- premium without visual noise
- emotionally expensive, not flashy

If a Figma frame is structurally correct but visually generic, it is not aligned.

---

## RULE 8 — DESIGN FOR REPOST, SCREENSHOT, AND COMPRESSION

All flagship surfaces and social objects must be tested under compression:
- full-size
- thumbnail
- screenshot of screenshot
- feed crop
- story crop
- bright-device context
- arm's-length readability

If the design only works full-size, it fails.
If the design loses its identity when shrunk, it fails.
If the hook disappears at thumbnail size, it fails.

---

## RULE 9 — EVERY SOCIAL OBJECT MUST HAVE A JOB

No export or visible share object gets designed without a primary job.

**Possible jobs:** AUTHORITY · TASTE · EDUCATION · REACH

Pick one primary. At most one secondary. Do not design one object to do all four.

---

## RULE 10 — THE USER MUST GET IDENTITY PAYOFF

Every major export or high-visibility UI surface must answer: **What does using or posting this say about the user?**

**Weak answer:** they used an app.

**Strong answer:** they know light / they have taste / they are serious / they understand craft / they are ahead / they know what matters.

If the surface does not create identity payoff, it is strategically weak.

---

## RULE 11 — FIGHT FOR ONE DOMINANT IDEA

No important design should have multiple equal-weight focal points. One thing must win. The rest supports it.

Ask: what is the first read? what is the second read? what is the third read? If that is unclear, the hierarchy is weak.

---

## RULE 12 — REMOVE BEFORE ADDING

When a design is weak, the first instinct should be: remove, reduce, quiet, harden, separate, re-rank.

Not: add more labels / effects / explanation / features / badges / motion.

Most weak work gets worse by adding.

---

## RULE 13 — FIGMA REQUIRED DELIVERABLES FOR BIG VISIBLE WORK

For any major visible pass, Figma work must include:
1. current state
2. proposed state
3. at least one rejected alternative or explicit rationale for why alternatives were not pursued
4. mobile frame
5. desktop frame when relevant
6. thumbnail/compression check
7. annotation of what changed and why
8. explicit statement of primary job
9. explicit statement of what is locked and what is intentionally not solved

---

## RULE 14 — REQUIRED SCORING FRAMEWORK

Every major visible design pass must score against these 10 categories, 1–10:

1. Distinctiveness
2. Hierarchy
3. Authority
4. Taste
5. Emotional hook
6. Screenshot/thumbnail resilience
7. Studio Matte alignment
8. Social/post-worthiness
9. Product identity clarity
10. Overall iconic potential

Then answer:
- Is this merely good?
- Is this strong?
- Is this iconic?
- What prevents it from being iconic?

If it is not iconic, say exactly why.

---

## RULE 15 — NO FALSE CONSENSUS

Do not protect the work from criticism.
Do not soften the critique to preserve momentum.
Do not call something excellent because it is improved.
Improved is irrelevant. The only question is whether it is strong enough.

---

## RULE 16 — BUILD ONLY AFTER VISUAL DIRECTION IS EARNED

Implementation follows visual conviction. Do not rush to code because the idea is "probably right." If Figma has not proved the hierarchy, composition, and emotional effect, the work is not ready for code.

---

## RULE 17 — REQUIRED RESPONSE FORMAT: DESIGN CRITIQUE

For any major visible design task:

1. **CURRENT_VERDICT** — blunt judgment, not summary
2. **PRIMARY_JOB** — what this surface/object is primarily supposed to do
3. **WHAT_WORKS** — only what is truly strong
4. **WHAT_FAILS** — exact weak points, no vague filler
5. **GENERIC_RISK** — where this is drifting into generic SaaS / premium-lite / template behavior
6. **ICONIC_POTENTIAL** — what would make this memorable, what is stopping that now
7. **FIGMA_REQUIREMENT** — what must be tested in Figma before implementation or lock
8. **NEXT_SINGLE_MOVE** — one next move only
9. **DO_NOT_DO** — traps to avoid

---

## RULE 18 — REQUIRED RESPONSE FORMAT: FIGMA DESIGN TASKS

For any Figma generation/update task:

1. **STATUS_CLASSIFICATION**
2. **EXECUTION_SCOPE**
3. **FIGMA_FRAMES_TO_CREATE_OR_UPDATE**
4. **EXACT_CHANGES**
5. **STUDIO_MATTE_ALIGNMENT**
6. **ICONIC_RISK_CHECK**
7. **ACCEPTANCE_CHECKLIST**
8. **NOTION_LOG_STATUS**
9. **CHANGE_LOG_APPEND**

---

## RULE 19 — ICONIC RISK CHECK

Every Figma pass must answer:
- Does this look unforgettable or merely polished?
- Does this feel like NGW or like a premium template?
- Does this create status for the user?
- Would this survive as a screenshot in the wild?
- Would another photographer actually repost this?

If those are weak, the pass is not done.

---

## RULE 20 — NOTION LOGGING IS REQUIRED

Every major visible design action must be logged in Notion. This includes: Figma creation, Figma updates, design audits, visual reviews, parity findings, design direction decisions, creative direction decisions, code commits affecting visible design, corrections of prior inaccurate design reports.

If Notion cannot be updated, state that explicitly and mirror the entry in CHANGE_LOG_APPEND.
